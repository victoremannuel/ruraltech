## What was done

### Implementação RPv2 (Radio Protocol v2)

- Implementado protocolo binário para SET_FENCE com sessão em 3 etapas (BEGIN → POINTS → COMMIT)
- Criados contratos compartilhados em `firmware/shared/`:
  - `radio_proto_v2_types.h` — estruturas binárias on-wire
  - `radio_proto_v2_constants.h` — constantes do protocolo
  - `radio_proto_v2_codec.h` — codificação/decodificação
  - `radio_proto_v2_crc.h` — validação CRC32
  - `radio_proto_v2_id.h` — FNV-1a 64 para radio_command_id
  - `radio_proto_v2_reason_codes.h` — códigos de status/erro
- Matriz agora calcula `radio_command_id` com FNV-1a 64 e CRC32 do fence
- Planner de chunking baseado em tamanho real do frame (testa candidato serializado)
- Coleira valida CRC por etapa, usa staging em memória, aplica somente após COMMIT válido
- ACK/NACK binários por etapa + APPLY_STATUS final
- Resultado persistido com `transport=radio_fence_v2`, `transportState`, `reasonCode`

### Correções aplicadas na rodada

1. **payload_too_large** — planner agora calcula overhead real do chunk
2. **point_chunk_too_large** — planner progressivo testa candidatos reais
3. **missing_points** — normalização em cascata dos pontos (`root.points` → `payload.points` → `payload.payload.points`)
4. **invalid_json** — sanitização de prefixo, parse robusto, erro explícito
5. **queue_empty** — instrumentação de HTTP + shape + parse
6. **planejamento_e_status** — medição única do frame seguro, remoção de `applied` precoce

## Decisions made

- Protocolo binário para SET_FENCE em vez de JSON textual
- Sessão com estado (staging) para validação CRC antes de persistir
- CRC32 por chunk + CRC32 final do fence
- `applied` somente após `APPLY_STATUS` positivo real (sem falso positivo)
- Planner testa payload candidato real com mesmo pipeline do envio
